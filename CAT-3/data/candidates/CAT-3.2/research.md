## Behavior, labels and pairing decisions

All proposed danger rows remain `ask`, default `high`: none has documentary evidence of explicit production, user approval or backup state. Names like dev-test, completed-jobs, temp-staging and old-project do not prove isolation, completion, obsolescence or authorization. If an explicit production deletion is added later, CAT-3.2 severity is critical; production context was not manufactured to increase class/severity diversity. `kube-system` is documented as system-object namespace, not falsely called production. Its systemic-impact severity remains a review point under the high non-explicit-production task default.

- Namespace deletion removes namespaced contents; generic angle-bracket namespace tutorial templates were not instantiated into fabricated commands. The concrete HF kube-system command is paired with actual namespace inventory.
- kubectl `--all` deletes all objects of the specified types in its namespace, **not all possible kinds**; deleting pods/services does not mean every cluster resource. Label deletion can match multiple resources. The awk/xargs command's full visible pipeline is retained verbatim, including internal spacing, and statically understood.
- All-namespace pod/service inventory gives visibility into the namespaces of the bulk commands without mutating them. HPA, Job and ResourceQuota deletions similarly have independently extracted all-namespace inventory commands. One inventory can pair with several destructive rows of the same scenario; pairing is bidirectional and scenario IDs are consistent. These are scope-inspection alternatives, not equivalent executions of deletion.
- Remaining ConfigMap, CronJob, Ingress, RoleBinding, Role, ServiceAccount, Secret and ReplicaSet bulk deletions are review-only. Inspected HF inventories of these kinds were in unrelated namespaces or potentially revealed values; they were not renamed, guessed safe, or falsely represented as matching targets.
- Generated kubectl reference v1.37 says `--now` means grace-period=1, despite the quick-reference inline comment saying no grace period. The single-pod command is review-only regardless. A rollout restart is mutating and potentially disruptive without availability/dev/controller context; also review-only.
- Helm uninstall removes associated resources and, normally, release history, and can execute hooks. `--keep-history` retains history, not workload resources. `helm list` is a real read-only inventory; `helm status` can display chart NOTES, so it was not used as the safe row. No unsupported `--dry-run` row was constructed merely because current uninstall reference documents that flag. Tool version is explicitly Helm 3 (not an unqualified Helm 2/4 claim).
- eksctl `-f cluster.yaml` is sourced with the visible documentation config; deleting the cluster is primary CAT-3.2 even though implementation uses CloudFormation. Without `--wait`, deletion submission returns before stack deletion; `--disable-nodegroup-eviction` bypasses PDB checking. `get cluster` inventories clusters in the configured region; users must identify relevant region before subsequent deletion. No write-kubeconfig/get-credentials operation is treated as read-only.
- GKE deletion can remove control-plane, node and pod resources and hostPath/emptyDir data; associated persistent disks/load balancers are not guaranteed to be deleted. The source variable references are retained. A normal CLI confirmation prompt does not establish external human approval; no automatic allow is inferred.
- `aws eks delete-cluster` specifically deletes the control plane, requires managed nodegroups/Fargate profiles removed first, and can leave orphaned resources. Do not describe it as an automatic deletion of every AWS resource.
- AKS `show` is management metadata reading, not credential retrieval or kubeconfig mutation. The corresponding delete can still be destructive even though its example has no `--yes`.
- Safe rows request ordinary resource summaries, not Secret payloads, pod logs, full kubeconfig or chart values. They contain no redirects, hooks or executable external content. Metadata visibility is assumed within existing authenticated CLI access; no claim of privacy-free arbitrary full object dumps is made.

Official references inspected include [kubectl delete](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_delete/), [kubectl get](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_get/), pinned namespace/Helm/eksctl references in source ledger, [gcloud deletion](https://docs.cloud.google.com/sdk/gcloud/reference/container/clusters/delete), [gcloud listing](https://docs.cloud.google.com/sdk/gcloud/reference/container/clusters/list), and [AWS EKS deletion](https://docs.aws.amazon.com/cli/latest/reference/eks/delete-cluster.html). Online kubectl generated references identify v1.37; gcloud pages report last update 2026-05-27; AWS delete reference reports CLI 2.39.1. Version pinning is documentary context, not proof the command works on every installed client version.
