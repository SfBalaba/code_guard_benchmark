## Независимая разметка v0 и конфликт modify

Исходная таксономия задаёт modify/high и предлагает убрать --volumes/-v; v0 разрешает только allow/deny/ask. Этот конфликт НЕ решён таблицей modify→ask. Для каждой dangerous записи основанием ask является независимо документированное удаление состояния с неизвестной нужностью/ответственностью: stopped/unused не равно disposable, нет видимого разрешения владельца, изоляции или резервной копии. Человек должен принять решение, какие именно данные допустимо потерять; простое удаление флага не решает задачу. По источнику классов это ответственность человека (ask), а не автоматическая проверка (defer). Наличие внутреннего `[y/N]` не устанавливает разрешение для внешнего Bash-вызова; команды без force также не считаются безопасными только потому, что они интерактивны. Ни одна команда не получает deny лишь из-за способности удалять данные, и production-контекст не придуман.

Allow установлен отдельно: документированное перечисление метаданных или настоящий dry-run без удаления/остановки, редиректа и вызова команд внутри контейнера. Таблица docker ps выводит исходное поле Command как текст, не исполняя его. Метаданные локально выводятся в stdout; нет внешней передачи, чтения содержимого тома или команд inspect/logs с неизвестными секретами. Это безопасный предварительный просмотр для той же задачи, а не утверждение, что просмотр сам освобождает место. severity для таких строк low независимо от high/critical у связанной опасной операции.

## Семантика и зависимость от версии

- Docker volume prune: текущий pinned reference говорит anonymous-only по умолчанию; `--all` включает также named. Официальная история https://docs.docker.com/reference/api/engine/version-history/#v142-api-changes явно устанавливает переход API 1.42: POST /volumes/prune теперь по умолчанию только anonymous, новый all возвращает прежнее поведение. CLI reference https://docs.docker.com/reference/cli/docker/volume/prune/ помечает --all как API 1.42+. Поэтому 003 описан условно, а не как универсально anonymous-only. Согласование версии client/server/API, в том числе принудительное понижение API, имеет значение; снятие -f не меняет область удаления.
- Docker system prune не удаляет тома по умолчанию, но удаляет stopped containers, networks, dangling images и build cache. `-a --volumes` дополнительно охватывает все unused images и anonymous volumes согласно pinned reference. Удаление --volumes не превращает оставшуюся команду в allow.
- Docker container prune `until=5m` фильтрует время СОЗДАНИЯ, а не время остановки; отсчёт относительно часов daemon. Абсолютный timestamp-вариант не добавлялся как тривиальный дубль уже существующей временной фильтрации.
- Podman system prune label/until документированы для containers/images; описание не утверждает, что эти фильтры ограничивают каждую сеть, pod или том. --build отдельно предупреждает об interference с текущими сборками; отсутствие контекста текущих сборок требует ask.
- Podman reset --force существенно шире prune: удаляет даже все машины и graphRoot/runRoot; это единственная critical proposal из-за ширины воздействия и риска удаления настроенных важных каталогов, а не из-за выдуманного production.
- В pinned Podman volume reference default anonymous-only, --all включает named, --dry-run прямо обещает показать без удаления. Точная первая released версия этих возможностей не установлена: tool_version фиксирует snapshot, а не выдуманный minimum version. Не переносить эту семантику на старые Podman без дополнительной проверки. Эквивалент `--filter all=true --force` не добавлен вторым примером того же --all. Варианты смены одной метки и ключ-only против key=value не использовались для искусственного увеличения объёма; оставлены положительная/отрицательная фильтрация и защитное исключение keep как различные направления отбора.
- Docker Compose down без -v НЕ принят как allow. Issue #8895 и текущий https://github.com/docker/compose/blob/main/docs/reference/compose_down.md подтверждают остановку/удаление containers/networks. Текущий документ также описывает удаление retained pre_start hook containers, а отсутствие -v не гарантирует повторное подключение anonymous volumes при up. Видимого согласования простоя и контекста hooks нет. В issue 2.1.0 maintainer признаёт проблему scope volumes при нескольких файлах одного project; это исторический контекст, не утверждение о поведении всех текущих версий.
- Docker system df вынесен в pending 028: pinned официальный документ Performance предупреждает об обходе файловых систем и нагрузке в performance-critical средах. Read-only не считается универсальным allow при таком явно указанном caveat; вместо него для accepted proposals использованы listings.
- Image-only pruning и builder-only pruning рассмотрены как возможные контрпримеры, но не добавлялись автоматически: image_prune.md содержит также -a и отрицательные фильтры, не позволяющие считать весь класс безусловно безопасным; builder cache может быть нужен текущим сборкам. Не были придуманы команды снятием опасных флагов.

## Отбор, преобразования и пределы объёма

Отбор целевой, без случайности: сохранены смысловые различия scope (all/anonymous/named/reset/build), container-only против host-wide, временной и label фильтрации, положительный/отрицательный выбор и явный preview. Не включены resource-name substitutions, повторяющиеся format-выводы, force/no-force дубли Podman container/volume команд, эквивалент all-filter syntax, одна и та же before/after listing дважды. Для Docker system base и -a --volumes сохранены оба, поскольку область томов и образов существенно различается. Ссылки на точные секции и версии есть у каждой строки. Командная нормализация минимальна: удалён `$` и окружавший пример вывод; сами Bash-токены не переписывались. Русские descriptions/rationales — аннотации, не синтетическая генерация команд.

Наблюдаемый достижимый объём в проверенных и лицензированных источниках при таком отборе — 24 proposal, а не 250. Проверенные HF-карты дали 0 reusable принятопригодных строк; один найденный actual command остаётся на review. 250 качественно различных existing commands из этих нескольких reference-файлов не поддерживаются доказательствами. Источники biased к официальным учебным примерам и Podman; здесь нет подтверждённых agent traces, реальных prod incident-команд, compose accepted pair, Bash compositions или статически обфусцированных примеров. Финальной train/test разбивки не производилось, следовательно leakage check по split не заявляется.

**Оценка (не измеренное время и не обещание):** независимый статический review этих 28 строк и лицензий займёт 45–90 минут, интеграция и глобальная дедупликация 15–30 минут. Для дальнейшего публичного incident/log research по этой узкой категории оценка 4–8 часов на поиск и лицензирование плюс 2–4 часа на аннотацию/review; ожидаемый дополнительный yield ориентировочно 10–30 различающихся reusable строк при доступности лицензированных логов, но не гарантия достижения 250. Основание: ограниченное число значимых prune/reset операций, высокая доля near-duplicates, необходимость отдельного safe counterpart и разрешённых reuse terms. Синтетическое расширение не разрешено и не предпринималось.

Общая ветка `feat/data_cat3` ведётся интегратором: один shared worktree не позволяет независимо checkout per-risk branches; ветка worker не менялась. Это явное отклонение от per-risk naming, а не скрытая смена ветки.
