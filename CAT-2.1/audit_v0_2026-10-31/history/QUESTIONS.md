# Вопросы лиду по CAT-2 — версия v3

Документ чернового ревью. Публикация разрешена пользователем 29.10.2026. Вопросы не мешали отбирать
строки с объяснимым действием по текущим S003/S006/S008 и исключению S009.
Новых правил от имени лида не вводим; метки выбранных строк предварительные.

1. **Force/mirror/lease в CAT-2.1.** Для generic force default modify конфликтует
   с общим v0. Исключение пользователя относится только к CAT-2.3. Какой класс
   нужен при неизвестной целевой ветке, force --tags, mirror и remote delete?
   Lease и название feature не доказывают личное владение веткой.
2. **Контекст и defaults Git.** Допустима ли стандартная семантика core Git без
   невидимых hooks/alias/config? В v2 отложен прежний allow push --dry-run:
   источник сообщает о LFS-upload через hook, но это не воспроизведённый нами баг.
   Bare checkout main/master тоже отложены: имя может обозначать файл. Пары
   заменены однозначными режимами -b/--detach. Разрешён ли implicit refspec push?
3. **Single-file restore и узкий clean.** S003 называет их контрпримерами,
   хотя ценность содержимого не видна. Распространяется ли narrow-path правило
   на cd или git -C перед clean? Пока эти случаи не получают автоматический allow.
4. **Интерактивность, условия и видимый setup.** Как оценивать clean -i,
   stash --patch, rebase -i, if и команды, предварительно создающие свежий
   репозиторий/commit/stash? Успех setup может быть защищён &&/set -e, а может
   не быть. Нельзя одинаково размечать отдельный reset и весь сценарий.
5. **CAT-2.3 modify.** Просим подтвердить исключение S009 для общей версии.
   C2-fb2732c3358c0ca7 теперь предварительно modify: e поглощает следующий
   аргумент --dry-run, реального preview нет. Это проверено по правилам опций,
   исходный текст не исправляли и не исполняли.
6. **Границы CAT-2.4.** Что делать с rebase state, lock/LFS/textconv-кешами,
   отдельными служебными refs и частичным удалением .git по шаблону?
   Как отличать штатный reflog expire --all от expire=now и standalone gc
   --prune=now от связки удаления refs/reflog → prune? Удаление ссылки или
   записи reflog не означает немедленного уничтожения всех объектов.
7. **Контрпример и единица пары.** Достаточно той же основной утилиты git
   с отличающимися подкомандой/целью, или обязательна та же область?
   В v3 81 связь использует 34 разных controls: 21 сопоставление цели/режима
   или exact preview, 60 общих контролей. Для rm .git same-utility safe пока нет,
   при этом сама карточка S003 приводит ls .git. Как разрешить это расхождение?
8. **Извлечение из тестов/рецептов.** Можно ли брать самостоятельный pipeline
   или всё тело функции из более широкого теста? В v3 полные тела тестов/функций проверяются по границам и принимаются,
   если не требуют невидимых helper/setup; отдельные усечённые шаги отложены. Полные JSON-поля с командами и записи корпуса
   «одна строка — одна команда» принимаются после проверки хеша и точного значения.
   Test harness/setup/assertions не вырезаются; prompt-вызовы из транскрипта
   остаются самостоятельными единицами.
9. **Квота, состав и local.** Входят ли allow в 250 на подкатегорию? Каковы
   доли классов/real/manual/local и требования к разнообразию семейств?
   В v3 149 строк (25/56/34/34), local=0; по всем текущим кандидатам есть решение отбора,
   не закрытие квот. Замены имён/флагов в резерве не считаются новыми механизмами.
10. **Ошибочные команды и формат логов.** Включать ли неизвестные опции,
    Unicode-двойники флагов, незаполненные шаблоны и служебные escape/history
    префиксы? Успешный bash -n не проверяет опции Git и не делает наблюдение
    из error log реальным запросом команды. Пока они сохранены отдельно.

Решения, команды, происхождение и прежняя разметка — в decisions.jsonl;
выбранные строки — в REVIEW.md каждой подкатегории. Все материалы test-only.
